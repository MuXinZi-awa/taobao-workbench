# 推广库存巡检（promo-stock-check）

把「ERP 在手库存」和「万相台推广单元」对撞，告诉你**哪些推广单元在推一个没货的品**。

## 它做什么

| 步骤 | 动作 |
|---|---|
| ① 拉数据 | 连 CDP 9222，抓 csrf，把 11 个推广计划的全部单元拉下来（约 30-60 秒） |
| ② 出表 | 按料号归一化匹配 ERP 在手，分成「该停 / 该开 / 认不出」三类 |
| ③ 执行停投 | 对「该停」那批执行暂停推广，每批 40 个，停完逐个读回状态 |

## 三类结果的含义

- **该停**：ERP 在手 = 0，且当前正在推广 → 在烧钱推一个没货的品
- **该开**：ERP 在手 > 0，但当前已暂停 → 有货却没推
- **认不出**：标题里找不到对应料号 → **一个都不动**，只列出来给人工看

## 为什么「认不出」不能自动处理

电商标题会把料号的连字符吃掉：`1-1586765-4` 写成 `115867654`。
ERP 里存的是带连字符的原样，两边归一化后变成一串没有分隔的数字，
**连字符该插在哪推不出来**（`115867654` 可能是 `1-158676-5-4`、`1-1586765-4`、`11-5867-654`）。

用「最接近」硬配，会把 A 的库存安到 B 头上——比不认更危险。

## 前置条件

1. **Chrome 在 9222 上，且已登录主店**（插件只连不开，不启动浏览器）
2. **ERP 全量表存在**：默认读
   `办公室工作\数据\ERP入库_全量_1026.csv`
   可用环境变量 `PSC_ERP_CSV` 覆盖路径
3. 该 CSV 需要 `料号` 列和 `在手数量` 列

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/plg/promo-stock-check/status` | 连接状态 + 缓存信息 |
| POST | `/api/plg/promo-stock-check/pull` | 拉全量单元 |
| POST | `/api/plg/promo-stock-check/check` | 对撞出三张表 |
| POST | `/api/plg/promo-stock-check/pause` | 执行停投（不带 ids = 全部「该停」） |
| POST | `/api/plg/promo-stock-check/pause?ids=1,2,3` | 停指定单元 |

## 踩过的坑（改代码前先看这几条）
1. **csrfId 只能从「页面自己发 findPage 的请求」里抓**。
   `window.g_config`、`window.mtop` 在这站全是 null。抓不到 csrf，接口一律 403
   （`bizLogin csrf检查未通过`）。

2. **批量提交单批上限 40**。实测：10 个 ✅ / 20 个 ✅ / 40 个 ✅ / **93 个 ❌**（读回 0/93，不报错）。
   原因是虚拟滚动列表，勾选超过一屏后 DOM 重建，已勾的丢了。

3. **不能认 click 返回值**。`cb.click()` 返回 true 不代表真的勾上了。
   必须数 `document.querySelectorAll('input[type=checkbox]:checked').length`。

4. **按钮文本带图标字符**。「批量修改状态」实际是 `批量修改状态\n\ue646`，
   用 `^批量修改状态\s*$` 精确匹配永远找不到。要用「包含」+ 取最窄可见元素。

5. **菜单两项可能塞一个节点**。有的计划状态菜单文本是 `正在推广\n\n暂停推广`（两项一体），
   有的是独立两项。所以匹配菜单项也只能用「包含」。

6. **翻页后每页条数会重置回 40**，不能按 100 算交集。

7. **标签页超过 10 个，页面操作会静默失效**——所有操作看起来成功，实际全无效。
   跑批前清标签，跑批中定期检查。

8. **浏览器只连不开**。自己 `launch_persistent_context` 会和上品/推广批次抢 profile 锁，
   而且登录态得重来。一律 `connect_over_cdp("http://127.0.0.1:9222")`。

## 「执行启用」为什么是灰的

菜单里确实有「正在推广」这一项，也点到了，但试点 **读回仍是 pause——没生效**。
原因还没查清（可能缺确认步骤，也可能点了没提交）。

**给一个不生效的按钮，比没有更糟**，所以先禁用。等验证通了再点亮。

9. **遮罩弹窗关不掉，所有批量操作都是空跑**。实在（2026-10-29）：
   那个 × 是 `DIV.bXMILLdiFw`，19×13 像素，**无 class 语义、无 aria-label、不是 button**，
   ESC 也关不掉。按 class / aria / 文本找关闭按钮全失效。
   **唯一可靠的办法是结构定位**：找全屏高 z-index 层 → 点它右上角 160×160 区域里
   最小的可见元素 → 回读确认遮罩真消失。实在不行就抬 `pointer-events:none`（不隐藏，用户仍可见）。

10. **插件改完不重启不生效**。workbench 的插件模块是进程启动时 import 一次的。
    改完 `server.py` / `_worker.py` 必须重启工作台（8900），否则跑的还是老代码——
    症状就是面板显示 `undefined`、或者拉数据还是旧的计划数。

11. **HTTP handler 线程里跑不了 asyncio**。报 `name 'base_events' is not defined`，
    playwright 一碰就死。所有浏览器活必须走 `_worker.py` 子进程。

## 计划列表不写死

调 `campaign/horizontal/findPage.json`（`pageSize: 200`）自动发现全部计划。
实测主店 **23 个计划**（关键词1–23），其中关键词12–14、16–23 是空壳（0 个单元），
真正有货的是关键词1–11（各 500 个，已满）+ 关键词15（25 个）。

硬编码 11 个的后果：只能看到半个盘子，另外 12 个计划里没库存的品还在烧钱而你不知道。

## 「执行启用」已验证

2026-10-29 实测：对 `ST730696-3`（84367142438，已停）执行启用 → `读回 start 1/1` →
再停回 → 接口终验 `displayStatus = pause`。两边都通。

批量启用还没跑（今天「该开」是 0 个，没场景），所以按钮能点，但批量这步未验。
