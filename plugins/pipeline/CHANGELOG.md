# CHANGELOG · 流水线（pipeline）

> 本文件依据 `manifest.json`、`README.md`、`_交接_*.md`、workbench 内核 `CHANGELOG.md`（插件版本跳变行）与脚本 mtime 补记。
> 版本号只写有明确出处者；无出处的改动标「未记载」，不臆测。

## 0.2.23 — 2026-10-17
- `pub` 加 **`force`** 参数（透传 `--force`）：商品已双百但图/视频是错的时候必须强推，
  否则永远被「已优化」跳过——错素材会一直挂到线上（修 W3S-1939-P012 时踩到）。
- `pub` 加 **`confirmed`** 参数（**只认显式传参**）：人工已确认“这批确实是新品、线上没有它”时跳过复核。
  闸的意义是防脚本自己猜，不是防人拍板。
- 保守闸升级：判「新品」但 state 有旧 id 的品，原为“两边都不做”（活就阁着），
  改为**按旧 id 走编辑**——编辑可撤销、新建不可撤销。

## 0.2.22 — 2026-10-17
- `scripts/_classify_one.py` 的命中判定改「边界匹配」：料号后紧跟 `-/_+字母数字` 不算命中，
  前面紧贴 ASCII 字母数字也不算；删掉 `hit = hit or rows[0]` 兜底，改为标「查询存疑」。**为什么**：原逻辑是去横线做子串——`W3S` 会命中 `W3S-1939-P012`、也会命中 `AW3S`
  （图库里这确实是五个不同产品，分开存的）；兜底拿第一个结果顶替更险，
  会把 A 的商品当成 B 的来改（1016 实锤：W3S 的素材/属性被改到了 W3S-1939-P012 上）。

## 0.2.21 — 2026-10-16
- `pub` 分支加「保守闸」：复核判「新品」但 state 里还留着淘宝 ID 的品，一律不新建、转待人工。**为什么**：卖家中心的在售搜索会漏掉已有商品（当天实测：`1241374-1` / `2-964296-1` / `W3S` 的买家页能正常打开、编辑页显示「基础100 扶优100」，搜索却搜不到）——而「新建」不可撤销，会变出同型号两个品；不确定时往可撤销那侧倒。

## 0.2.20 — 2026-10-16
- `pub`（上品/优化）加「上品前复核」硬闸：动手前先跑一次 `classify`，把 state 的 type/id 按线上重判，再按新 type 分流；复核失败不阻断但写日志。**为什么**：state 会过时——分流查的时候线上没货、后来货上了、state 没回写，面板仍当它「新品-待上架」，于是走新建 → 同型号两个品（当天实测：33 个「新品-待上架」里 13 个线上已有货）。
- `auto_campaigns` 改读 sqlite 状态库（`state_db.get_plans`），与 tg-monitor「刷新容量」同源，并过滤非数字键。**为什么**：刷新容量写库、面板读 `plan_state_<mid>.json`，而 json 已停更——加的计划越多越读不到（当天实测：库里 25 个计划，json 只剩 12 条 9-22 旧数据，含一条 `"10计划"` 残渣被当成可投计划）。
